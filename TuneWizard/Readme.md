## Мастер настройки

Пошаговый мастер настройки Copter и QuadPlane (VTOL-часть ArduPlane) по одному логу `.bin`: проверка лога, спектр гироскопов, гармонический notch, низкочастотные фильтры, PID по осям, сводка и файл параметров. Помнит прошлый проход аппарата: на следующем логе показывает, что из предложенного применено и сбылся ли прогноз. До полёта проверяет параметры (по логу или по файлу `.param`): будет ли в следующем логе всё нужное для настройки. У QuadPlane шаг 4 (PID) пока закрыт — раздел «QuadPlane (VTOL-часть ArduPlane)». Объединяет расчёты FilterReview и PIDReview; оригинальные инструменты не изменяет.

Дизайн: `docs/plans/2026-10-23-tune-wizard-design.md`, QuadPlane — `docs/plans/2026-10-30-tune-wizard-stage9-design.md`. Планы этапов — в `docs/plans/`.

### Запуск

Двойной клик по `Мастер настройки.cmd` в корне репозитория (Windows 10/11, Python не нужен): он запускает локальный сервер на PowerShell `TuneWizard/windows/serve.ps1` и открывает `http://127.0.0.1:8000/TuneWizard/` в браузере по умолчанию. Пока мастер работает, открыто окно консоли «Мастер настройки — 127.0.0.1:8000» с адресом и папкой; чтобы остановить сервер — закройте окно (открытая вкладка перестанет загружать файлы, уже загруженная страница работает до перезагрузки). Порт всегда 8000 и адрес `127.0.0.1`: память прохода привязана к адресу страницы, поэтому другой порт мастер не берёт.

Если порт уже занят мастером этой папки (её окно `.cmd`) или `python -m http.server` с мастером (в том числе F5 из VS Code), просто откроется вкладка, второй сервер не поднимается; мастером другой папки (например, переносной) или чужой программой — сообщение в окне: закройте окно того мастера или ту программу и запустите снова.

Или из корня репозитория: `python -m http.server --bind 127.0.0.1`, затем `http://127.0.0.1:8000/TuneWizard/` — или главная WebTools `http://127.0.0.1:8000/` и иконка в строке «Мастер настройки» (первая в списке инструментов; в `index.html` в корне добавлена только она).

Из VS Code: F5 с конфигурацией «Мастер настройки (python + Chrome)» (`.vscode/launch.json`) — она запускает тот же сервер задачей `Host` и открывает страницу мастера в Chrome с отладчиком; остановка отладки (Shift+F5) гасит сервер. Открывайте мастер всегда по одному адресу (`127.0.0.1`, не `localhost`): память прохода привязана к адресу страницы.

Иконка этой строки — `images/TuneWizard_Icon.png`, ширина 400 px (на главной показывается в 200 px, двойная плотность — для чётких экранов). Это снимок шага 2 на тестовом логе: полоса шагов и под ней спектр, в окне 760 px, где полоса шагов встаёт в две строки. Её делает скрипт `tests/tunewizard-icon.cjs`; обновить иконку, если вид шагов заметно изменился: `CHROME_PATH="C:/Users/<пользователь>/AppData/Local/Google/Chrome/Application/chrome.exe" npm run tunewizard:icon` (нужны те же лог и python, что для браузерного теста), посмотреть картинку и закоммитить файл. В обычные проверки скрипт не входит — иначе каждый прогон менял бы картинку.

### Переносная папка для других пилотов

**Зачем.** Мастером пользуются и другие пилоты — без репозитория, Git и Python. Для них собирается папка с мастером, FilterReview и PIDReview, которая запускается тем же двойным кликом по `Мастер настройки.cmd`. Дизайн — `docs/plans/2026-10-30-tune-wizard-stage8-design.md`.

**Сборка.** `npm run tunewizard:portable` (Windows, нужны git, Node.js и один раз `npm ci`) собирает в `dist/` (он в `.gitignore`) папку «Мастер настройки <ГГГГ-ММ-ДД> <коммит>» и zip того же имени рядом; `npm run tunewizard:portable -- --out <папка>` — в папку вне репозитория (внутри репозитория — только `dist/`). Незакоммиченные изменения в файлах состава — предупреждение и «+изменения» в имени и версии. Прежняя сборка с тем же именем удаляется и собирается заново. Скрипт печатает путь, число файлов, размер папки и архива и команду теста сервера на собранной папке. В обычные проверки сборка не входит, как скрипт иконки.

**Что внутри.** Мастер (`TuneWizard/` без `logs/`), `FilterReview/` (с `params.json` — описаниями параметров мастера) и `PIDReview/` целиком — кнопки «Открыть в …» работают без интернета; из `Libraries/`, `modules/` (парсер логов, Plotly, FFT, подсказки) и `images/` — только нужные этим трём страницам файлы (список `single_files` в `tests/tunewizard-portable.cjs`); в корне — `Мастер настройки.cmd` и `Прочитай меня.txt` (что это, кнопки FilterReview и PIDReview на невключённые инструменты, как запустить и остановить, вопросы Windows, браузер, память прохода, что делать, если мастер не запустился, версия — дата и коммит). Около 5 МБ, архив — около 1.6 МБ; файлы лежат в корне архива, без верхней папки: «Извлечь все» Проводника само кладёт их в папку с именем архива.

**Защиты сборки.** После копирования проверяются ссылки собранной папки: у каждого относительного `src`/`href` трёх страниц и у строковых `import(`, `fetch(`, `load_param_inputs(`, `step_open_in(` в их скриптах должен быть файл — иначе ошибка с перечнем, папка удаляется, архива нет (новый файл из `Libraries/`, `modules/` или `images/` — дописать в `single_files`). Логи пилота в архив не попадают: `TuneWizard/logs/` исключена, а файл `.bin`, игнорируемое git в папках состава (копии, резервные файлы) или символьная ссылка — ошибка сборки.

**Раздача.** Пилоту — один zip из `dist/` (папку рядом не нужно); перед отправкой можно проверить собранную папку командой, которую печатает сборка: `node tests/tunewizard-serve.cjs "<папка>"`. В git и на GitHub архив не попадает.

**У пилота** (как в «Прочитай меня»).

1. Правой кнопкой по архиву — «Свойства»; если внизу есть отметка «Разблокировать» — отметить и «ОК» (тогда Windows не задаёт вопросов при запуске). Затем правой кнопкой — «Извлечь все…» — «Извлечь». Из окна архива файлы не запускаются: запущенный оттуда `.cmd` пишет «Распакуйте весь архив».
2. Дважды щёлкнуть `Мастер настройки.cmd` (в Проводнике со скрытыми расширениями — «Мастер настройки»): откроется чёрное окно консоли — не закрывать его, пока работаете; мастер откроется в браузере по адресу `http://127.0.0.1:8000/TuneWizard/`.
3. На шаге 0 выбрать лог `.bin`.

При первом запуске файла из интернета Windows может спросить «Запустить этот файл?» — «Запустить»; синее окно «Система Windows защитила ваш компьютер» — «Подробнее», затем «Выполнить в любом случае». Закончив — закрыть окно консоли. Другое сообщение в окне (не из раздела «Если мастер не запустился») пилот фотографирует и присылает тому, от кого получил архив.

**Ограничения.** Только Windows 10/11 с PowerShell (5.1 есть в системе). Браузер — Chrome или Edge (мастер проверяется в Chrome, у Edge тот же движок); открывается браузер по умолчанию — если он другой, адрес надо открыть в Chrome или Edge вручную. Кнопки самих FilterReview и PIDReview на невключённые инструменты («Hardware Report», «MAGFit», «Open in filter tool») работают только на сайте WebTools, а UAV Log Viewer — сайт, ему нужен интернет; без интернета шрифты страницы — системные. Сервер однопоточный (запросы по одному) — он для одного пилота на этом компьютере. Память прохода — в браузере для адреса `http://127.0.0.1:8000`, а не в папке: новая версия папки её видит.

**Безопасность.** Сервер слушает только `127.0.0.1` (с других компьютеров недоступен, без прав администратора и окна брандмауэра), отдаёт только файлы своей папки методами GET и HEAD (выход за неё — 403); браузерный запрос с чужим адресом (`Host` не `127.0.0.1` и не `localhost` с портом) — отказ, иначе страница чужого сайта могла бы читать файлы папки через DNS rebinding; запрос без `Host` (HTTP/1.0) пропускается.

### Структура

- `index.html`, `wizard.js` — страница, состояние, навигация по шагам, шаг 0 (лог, вид аппарата и его профиль — `state.kind`, `state.profile`, проверки, график полёта; блок «Прошлый проход» строит `steps/memory.js`, блок «Подготовка к следующему полёту» — `steps/prep.js`); шаг, которого нет у аппарата (у QuadPlane — 4), в полосе шагов выключен с подсказкой.
- `plots.js` — реестр графиков Plotly: цвета из токенов CSS применяются ко всем графикам разом. Тема одна — только тёмная тема «Графит» (решение пользователя 24.10.2026).
- `steps/common.js` — общий модуль шагов: подписи, плитки и ячейки таблиц, вердикт, досчёт шага 1, контекст итога и отпечаток входов принятого шага (`step_summary_context`, «устарело» — `step_accepted_stale`), запуск действий с перехватом ошибок, «Открыть в …», описания параметров из метаданных (и флаг сбоя их загрузки), каркас механизма правок полей шагов 3–4, куски графиков.
- `steps/step1.js` — шаг 1 «Спектр до фильтров»: панель настроек спектра как в FilterReview, средний спектр, спектрограмма, таблица пиков с происхождением; у tailsitter — заметка об осях гироскопа.
- `steps/step2.js` — шаг 2 «Гармонический notch»: варианты настроек со сравнением, форма параметров с описаниями ArduPilot, бодэ, метрики, сохранение и загрузка `.param`.
- `steps/step3.js` — шаг 3 «Низкочастотные фильтры»: размер винта (у QuadPlane его нет), варианты со сравнением, форма параметров с описаниями ArduPilot, спектр гироскопа после фильтров, спектр D-составляющей, бодэ путей P и D, «Принять».
- `steps/step4.js` — шаг 4 «PID по осям»: вкладки осей и сводка, вердикт и плитки метрик оси, проверки качества измерения, варианты с прогнозом, форма `ATC_RAT_*_P/I/D` с описаниями ArduPilot, отклик на ступеньку, цель и факт, спектр D и выхода, бодэ разомкнутого контура, «Принять», «Открыть в PIDReview».
- `steps/step5.js` — шаг 5 «Сводка»: плитки, вердикт, принятое на шагах 2–4 (принят, не принят, устарело — с кнопкой «К шагу N», недоступен — шаг закрыт для аппарата), параметры «было → станет» и расхождения шагов, свёрнутый список без изменений, «что сделать перед следующим полётом», «Скачать .param», «Запомнить проход», «Печать».
- `steps/memory.js` — память прохода на странице: сохранение прохода, блок «Прошлый проход» шага 0, строки сравнения с прошлым проходом на шагах 2–4.
- `steps/prep.js` — блок «Подготовка к следующему полёту» шага 0: «Проверить .param…», источник параметров (файл или лог) и его вид аппарата (Copter или QuadPlane; файл и лог разных видов — отказ), цель полёта, список проверок и вердикт, таблица положений переключателя и выбор положения для ACRO, «Скачать .param исправлений», план полёта, «Печать плана»; пункты подготовки для сводки шага 5 (`prep0_summary`).
- `core/` — математика без DOM; те же файлы гоняются под Node:
  - `vehicle.js` — профиль аппарата (грузится первым из `core/`): одна таблица на вид — всё, чем для мастера различаются Copter и QuadPlane (шаги, префиксы `ATC_`/`Q_A_` и `MOT_`/`Q_M_`, сообщения PID и бит их полной частоты, ряды газа, VTOL-режимы и имена режимов, режим Acro и режимы выхода из него, заводские фильтры ПИД и пределы ускорения, оси гироскопа tailsitter, `SCHED_LOOP_RATE` по умолчанию, где учится газ висения), с источниками в коде ArduPilot; вид лога (`vehicle_kind`) и файла `.param` (`vehicle_kind_of_params`);
  - `log.js`, `checks.js` — сведения о логе (в том числе строка полётного контроллера, номер платы и рама; вид аппарата, газ и окно полёта по профилю — у QuadPlane самый длинный участок VTOL-режимов) и проверки пригодности;
  - `gyro.js`, `filters.js`, `spectrum.js`, `tracking/*.js` — перенос расчётов FilterReview «минимальным диффом» (загрузка IMU, FFT, фильтры, трекинг notch, спектрограмма);
  - `autofit.js` — автоподбор первого notch (PR ArduPilot/WebTools#363);
  - `metrics.js` — пики спектра и их происхождение (порядковый спектр, запасной метод — медиана частоты моторов);
  - `candidates.js` — варианты notch, оценка шума после фильтров и задержки, выбор лучшего;
  - `lowpass.js` — низкочастотные фильтры: формулы по размеру винта, варианты, оценка (шум гироскопа, шум D-составляющей, задержка путей P и D, бодэ) и отметки;
  - `pid.js` — перенос PIDReview «минимальным диффом» (загрузка `PIDR/PIDP/PIDY` или `RATE`, наборы параметров, пакеты, FFT компонент, отклик на ступеньку); отклик PIDReview — только для графика и сравнения с PIDReview;
  - `pidtune.js` — шаг 4: отклик КИХ МНК, проверки качества измерения, метрики отклика, шум D, режим лога, правила, модель регулятора `AC_PID`, прогноз и его достоверность, варианты и отметки;
  - `params.js` — файл параметров и битовые маски;
  - `summary.js` — итог прохода: строки «было → станет» по принятому на шагах 2–4, порядок источников, текст `.param` из изменённых, отпечаток входов и «устарело», «что сделать перед следующим полётом»;
  - `passmem.js` — память прохода: формат и хранилище, ключ аппарата, запись прохода, «применено», условия строки сравнения;
  - `prep.js` — подготовка к следующему полёту: правила по цели полёта и профилю аппарата с источниками (у Copter 13, у QuadPlane 10), положения переключателя `FLTMODE1–6` и предложение положения для ACRO, значения файла исправлений (маски складываются), имена с перезагрузкой, план полёта, имя `_prep.param`.
- `windows/serve.ps1` — локальный сервер для Windows (PowerShell 5.1, `TcpListener` на `127.0.0.1`, UTF-8 с BOM): его запускает `Мастер настройки.cmd` в корне репозитория или переносной папки; параметры `-Root` (по умолчанию — два уровня выше скрипта), `-Port` (8000), `-NoBrowser` (для теста).
- `logs/` — локальные логи и скриншоты для проверок, в репозиторий не попадают.

### QuadPlane (VTOL-часть ArduPlane)

**Что поддержано.** Мастер настраивает Copter и VTOL-часть ArduPlane — QuadPlane (решение пользователя 30.10.2026); самолётная часть (крыло, `RLL_RATE_*`, `PTCH_RATE_*`) — нет. Вид лога — по `VER.BU` и параметрам: 2 — Copter; 3 и `Q_ENABLE` ≥ 1 — QuadPlane (он поднимается при любом ненулевом `Q_ENABLE`); tailsitter — `Q_TAILSIT_ENABLE` > 0. Лог Plane без `Q_ENABLE` — СТОП «Аппарат» на шаге 0: «мастер поддерживает Copter и QuadPlane», что сделать — «Загрузите лог ArduCopter или ArduPlane с Q_ENABLE ≥ 1». У QuadPlane — шаги 0–3, сводка (шаг 5) и подготовка к полёту; шаг 4 пока закрыт (ниже). Всё, чем виды различаются, собрано в таблице профилей `core/vehicle.js` с источниками в коде ArduPlane; у Copter всё как раньше. Дизайн — `docs/plans/2026-10-30-tune-wizard-stage9-design.md`.

**Шаг 0.** Плитка «Аппарат» — «QuadPlane» (у tailsitter — «QuadPlane · tailsitter»), плитки «Висение VTOL» и «Средний газ VTOL»; газ на графике полёта — VTOL-моторов: `QTUN.ThO`, без него `RATE.AOut` (`CTUN.ThO` у Plane — самолётный мотор, в висении около нуля). Интервал по умолчанию — участки VTOL-режимов 17–23 (QSTABILIZE, QHOVER, QLOITER, QLAND, QRTL, QAUTOTUNE, QACRO) по `MODE`: соседние VTOL-режимы склеиваются в один участок, внутри участка — от первого до последнего ненулевого газа с отступом 1 с, берётся самый длинный участок, остальные называет проверка «Полёт» («ещё VTOL: …»); подпись под полями интервала говорит об этом. В логе нет `MODE` — окно по газу за весь лог, с оговоркой в проверке «Полёт». Проверки, которые у QuadPlane свои:

- «Сообщения PID VTOL» — PIQR/PIQP/PIQY (PIDR/PIDP/PIDY у Plane — самолётные регуляторы) и частота PIQR: от 99 Гц — OK, ниже — ВНИМ с советом включить бит 20 ATTITUDE_FULLRATE в `LOG_BITMASK` для будущего шага 4 (без него PIQx пишутся с частотой 25 Гц при бите ATTITUDE_FAST, 10 Гц при одном ATTITUDE_MED, а без обоих не пишутся вовсе); бита PID у Plane нет, бит 12 — CAMERA, его мастер не советует; PIQx нет — ВНИМ (шагу 4 QuadPlane эта проверка пока не нужна);
- «Полёт» — «Висение VTOL N с (от–до, режимы), средний газ …» и другие VTOL-участки; VTOL-участков с газом нет — СТОП «VTOL-полёта в логе нет»;
- «Газ висения» — `Q_M_THST_HOVER` против среднего газа VTOL-окна (допуск 0.05, как у Copter); совет — `Q_M_HOVER_LEARN = 2` и висение не меньше 30 с в QHOVER или QLOITER: газ висения учится только при работающем регуляторе высоты (QHOVER, QLOITER, QLAND, QRTL, VTOL в AUTO и GUIDED; в QSTABILIZE и QACRO газ ручной) и только при оценке воздушной скорости ниже 0.3·`AIRSPEED_MIN`, вертикальной скорости меньше 0.6 м/с, крене и тангаже меньше 5° (`ArduPlane/quadplane.cpp:1948–1953`; оценка — от датчика скорости, без него — по скорости GPS и оценке ветра, без обоих её нет; на логе не проверено).

Остальные проверки — общие с Copter, в том числе «До/после фильтров» (правило batch «бит 0 с битом 2» — по типу гироскопа, раздел «Как готовить следующий полёт»).

**Шаги 1–2** — как у Copter, по VTOL-интервалу (notch по газу у Plane — от газа VTOL-моторов, трекинг читает `Q_M_*`). `SCHED_LOOP_RATE`, если его нет в логе, — 300 (заводское при `Q_ENABLE`), а не 400. У tailsitter под спектром шага 1 — заметка об осях: регулятор VTOL работает в виде, повёрнутом на 90° по тангажу, поэтому ось Z гироскопа — крен VTOL, Y — тангаж, X — рыскание (со знаком минус).

**Шаг 3** — без размера винта и рекомендации, с именами `Q_A_*` (раздел «Как шаг 3 выбирает низкочастотные фильтры»). **Шаг 5 и память** — с именами `Q_A_*` и видом аппарата в ключе памяти (разделы «Как шаг 5 собирает итог» и «Память прохода»). **Подготовка к полёту** — правила QuadPlane и лог QACRO для будущего шага 4 (раздел «Как готовить следующий полёт»).

**Шаг 4 пока недоступен.** Кнопка шага 4 в полосе шагов выключена; подсказка на ней и строка сводки: «Шаг 4 (PID) для QuadPlane пока недоступен: метод ещё не проверен на логе QuadPlane, для него нужен лог полёта в QACRO с PID на частоте цикла. Подготовьте такой лог в «Подготовке к следующему полёту» (цель «PID»); шаг 4 появится следующим этапом». По логу пользователя (PIQx 24 Гц, весь полёт в QSTABILIZE) контур скорости не измерить; тестовый полёт — QACRO при `ACRO_LOCKING = 0` (только контур скорости, как Acro «Rate Loop Only» у Copter).

**Ограничения.**

- VTOL-участки внутри AUTO и GUIDED (VTOL-взлёт, посадка, удержание) по `MODE` не видны: в интервал по умолчанию они не входят, и шаги 1–3 их не берут — такой участок задайте вручную.
- QRTL — VTOL-режим, но на заходе (фазы QPOS_APPROACH и AIRBRAKE) аппарат летит по-самолётному: самолётный заход может попасть в склеенное VTOL-окно (QHOVER → QRTL). На логе не проверено — проверьте интервал на графике полёта.
- Вибрации и clipping — по всему логу, вместе с самолётным полётом, а не по VTOL-окну.
- Tailsitter: оси гироскопа — крен Z, тангаж Y, рыскание −X (заметка шага 1, шум D крена на шаге 3 — по оси Z); `Q_TRIM_PITCH` ≠ 0 слегка смешивает оси крена и рыскания — модель считает трим нулевым.
- Не рассматриваются: notch в самолётном полёте (бит 5 `INS_HNTCH_OPTS`), QAUTOTUNE и SystemID Plane, запасной ряд «Высота» графика полёта без `POS` (`QTUN.BAlt`; у Copter без GPS так же).
- Проверено на одном логе QuadPlane (третий лог проекта: ArduPlane 4.6.3, tailsitter `QUAD/X`, весь полёт в QSTABILIZE): полный цикл памяти прохода («было → прогноз → в этом логе») на QuadPlane не проверен.

### Как шаг 2 выбирает настройки notch

Мастер считает варианты: как в логе; автоподбор по методу PR #363; автоподбор с гармониками из лога; настройки лога с ослаблением из автоподбора; при необходимости — второй статический notch на оставшемся резонансе рамы (ширина — удвоенная ширина пика по уровню −3 дБ, от 10 Гц до 0.5·F). Каждый вариант оценивается по ожидаемому шуму после фильтров на главных пиках и в полосе 20–400 Гц и по фазовой задержке на 10 и 30 Гц. Рекомендуется самый тихий по полосе среди тех, что не ухудшают ни один пик больше чем на 3 дБ и задержку на 30 Гц больше чем на 0.5 мс относительно лога; иначе — настройки лога. Таблица вариантов видна целиком, любой вариант применяется одной кнопкой.

Если notch лога не работает (выключен, режим неизвестен или у источника трекинга нет данных), опора «как в логе» — лог без notch: допуск задержки +0.5 мс не применяется, задержки показаны к логу без notch, об этом говорят вердикт и подпись таблицы; notch лога включён, но смоделировать его нельзя — рекомендации нет, таблица остаётся для справки. `INS_GYRO_FILTER` формы выше 0.4 частоты гироскопа модель считает с ограниченным срезом, как прошивка (с предупреждением), а `SCHED_LOOP_RATE` не больше нуля и маски вне диапазона возвращаются к значениям лога. `INS_*_ESCMSK` показывается и пишется в файл, если он записан в логе или версия фильтра не ниже 4 — тем же правилом его берут значения лога шага 1, notch-база шага 3, сводка шага 5 и память прохода. «Принять» без «Применить вариант» принимает значения лога — вердикт тогда называет рекомендованный вариант.

### Как шаг 3 выбирает низкочастотные фильтры

У Copter размера винта в логе нет: его вводят вручную (4–40″, иначе предупреждение у поля), мастер запоминает его в браузере и подсказывает, какому размеру по формуле соответствует текущий `INS_GYRO_FILTER`. По размеру p в дюймах значения считаются по формулам Mission Planner (Initial Parameter Setup): `INS_GYRO_FILTER = max(20, round(289.22·p^−0.838))`; `FLTT` и `FLTD` крена и тангажа и `FLTT` рыскания — `max(10, INS_GYRO_FILTER / 2)`; `FLTE` крена и тангажа 0, рыскания 2; `INS_ACCEL_FILTER` 10. Пределы ускорения по формуле предлагаются, только если в логе заводские 1100 / 270 °/с²; иначе остаются из лога, потому что их записывает AutoTune. Имена и единицы — по логу: `ATC_ACCEL_*_MAX` в сантиградусах/с² (4.6 и раньше) или `ATC_ACC_*_MAX` в °/с² (новые версии).

Варианты: «Как в логе»; «По размеру винта» (рекомендуется; без размера винта его нет, и рекомендации тоже); «Лог + правило /2» — `INS_GYRO_FILTER` лога, `FLTT` и `FLTD` по правилу /2; «Свой» — значения формы после ручной правки. Notch — принятый на шаге 2, иначе из лога. Метрики показываются относительно «Как в логе»: шум гироскопа после фильтров в полосе 20–400 Гц (как на шаге 2); шум D-составляющей крена и тангажа — модель контура: спектр гироскопа после фильтров сворачивается к `SCHED_LOOP_RATE / 2` и умножается на производную ошибки и фильтры ПИД `FLTE` и `FLTD` первого порядка, как в `AC_PID.cpp`; задержка на 10 и 30 Гц путей P (фильтр гироскопа, notch, `FLTE`) и D (ещё и `FLTD`). `FLTT` стоит на цели и в метрики не входит, рыскание — по правилу, без метрик.

Отметки «шумнее лога» (шум гироскопа или D больше чем на 3 дБ) и «медленнее лога» (путь P или D больше чем на 1 мс на 30 Гц) предупреждают, но выбор не блокируют. При Kd оси 0 — «D выключен»: шум D и путь D этой оси не сравниваются; Kd нет в логе — «неполные данные». Вердикт предупреждает о том, чего модель не учитывает: notch-фильтр ошибки ПИД (`ATC_RAT_RLL/PIT_NEF` ≠ 0) и быстрый поток контура скорости (`FSTRATE_ENABLE` > 0). «Принять» не принимает пустые поля, отрицательные частоты и отрицательные пределы ускорения; файла `.param` на шаге нет — итоговый файл собирает сводка (шаг 5).

Форма при первом показе берёт `INS_GYRO_FILTER`, принятый на шаге 2, если он отличается от лога (итог берёт этот параметр у шага 3, иначе правка шага 2 терялась) — в таблице это строка «Свой»; «Применить вариант» перезаписывает поле, и заметка напоминает, что в файл пойдёт значение формы. `INS_GYRO_FILTER` выше 0.4 частоты гироскопа прошивка ограничивает — метрики считаются с ограниченным срезом, об этом заметка. Принят не рекомендованный вариант (например, «Как в логе» без «Применить вариант») — вердикт называет рекомендованный; смена размера винта после «Принять» принятое не старит: от размера зависят варианты, а не оценка принятого.

**У QuadPlane** формулы по размеру винта нет: для `Q_A_RAT_*` источника нет (в ArduPilot — только примеры `.param` в `Tools/Frame_params/QuadPlanes/`), поэтому поля размера винта, варианта «По размеру винта» и рекомендации нет (решение пользователя 30.10.2026); заголовок, вступление и заметки шага это говорят. Варианты — «Как в логе», «Лог + правило /2» (то же правило /2: для QuadPlane своего источника нет, а регулятор тот же — `AC_AttitudeControl_Multi`) и «Свой», метрики те же; вердикт сравнивает «Лог + правило /2» с логом, выбор — за пользователем (при строке «Свой» вердикт подсказывает, как вернуться к логу). Имена — с префиксом профиля: `Q_A_RAT_{RLL,PIT,YAW}_{FLTT,FLTE,FLTD}`, `Q_A_RAT_*_D`, `Q_A_RAT_*_NEF`; пределы ускорения — `Q_A_ACCEL_{R,P,Y}_MAX` (4.6, сантиградусы/с²) или `Q_A_ACC_{R,P,Y}_MAX` (4.7 и новее, °/с²) — по тому, что записано в логе; `INS_GYRO_FILTER` и `INS_ACCEL_FILTER` — общие. Пределы ускорения — только из лога (правятся в форме — строка «Свой»). Параметра нет в логе — заводское значение QuadPlane: FLTD крена и тангажа 10 Гц, остальные фильтры — как у Copter; пределы 400 / 400 / 100 °/с² (при `Q_FRAME_CLASS = 10` крен и тангаж — 300). Описания `Q_A_<X>` в форме — описания `ATC_<X>` (тот же регулятор). У tailsitter шум D крена VTOL считается по оси Z гироскопа (подпись графика D — «Крен VTOL (Z)», цвет оси Z). Предупреждение о `Q_A_RAT_RLL/PIT_NEF` ≠ 0 — как у Copter; `FSTRATE_ENABLE` у Plane нет. На третьем логе проекта «Как в логе» — `Q_A_RAT_*_FLTD` 25.5, `INS_GYRO_FILTER` 40, пределы 70000 / 70000 / 28800 сантиградусов/с²; «Лог + правило /2» — FLTT и FLTD 20.

### Как шаг 4 предлагает PID

Раздел — про Copter: у QuadPlane шаг 4 пока закрыт (раздел «QuadPlane (VTOL-часть ArduPlane)»). По каждой оси мастер измеряет отклик контура скорости на ступеньку методом КИХ МНК: импульсная характеристика «цель → факт» длиной 1 с подбирается методом наименьших квадратов во времени по окнам, где цель не меньше 20 °/с, а отклик — её накопленная сумма. Отклик PIDReview для этого не годится: его плато ниже 1 даже при идеальном слежении, а перерегулирование сжато к 5–20 %, поэтому он остаётся на графике только для сравнения. По отклику КИХ считаются нарастание 10–90 %, перерегулирование, установление в ±5 % от плато, остаточные колебания; по спектру D — шум D-составляющей выше 50 Гц (выше −40 дБ от выхода — предупреждение «горячие моторы» с советом снизить D или `FLTD`).

Измерение проверяется тремя проверками качества: (а) отклик почти не меняется при более сильной регуляризации; (б) первая и вторая половины данных дают тот же отклик; (в) нет подписи углового контура (|T| на 4–12 Гц не выше 1.5). Ещё нужно не меньше 10 с отобранных данных, иначе — «мало манёвров». В обычном полёте Acro при `ATC_RATE_FF_ENAB = 0` угловой контур подмешивается в цель скорости выше 4–5 Гц, и измерение обычно ненадёжно (так у всех осей тестового лога). Тогда отклик показывается с пометкой, правил и прогноза нет, а вердикт советует тестовый полёт: Acro с `ACRO_OPTIONS` «Rate Loop Only» (значение 2, или 3 вместе с Air-mode) и `ACRO_TRAINER = 0` (тренер подмешивал бы в цель выравнивание по углу), 2–3 минуты резких отклонений стиков по каждой оси, в `LOG_BITMASK` включены ATTITUDE_FAST и PID. Такой лог (весь интервал в ACRO с битом «Rate Loop Only») мастер распознаёт и считает точно: проверка (в) там не применяется, а I в модели регулятора с Copter 4.7 умножается на `ATC_ANG_*_P`, как в прошивке. Если интервал анализа шире участка ACRO (взлёт и посадка в STABILIZE), вместо совета слетать снова под сводкой шага появляется кнопка «Интервал — участок ACRO», которая сужает интервал анализа до него.

Коэффициенты «как в логе» — набор, действовавший в интервале анализа. Если после интервала PID менялись (AutoTune сохраняет их при дизарме, правка после посадки), строка таблицы называется «Набор интервала», подписи полей показывают и значения конца лога, вердикт предупреждает, а принятое перепишет значения конца лога — сводка помечает такие строки и пишет об этом в вердикте. Запас фазы, который нельзя определить (развёртка фазы недостоверна), показывается как «не определён», а не как неустойчивость.

Правила — только на надёжной оси, одно изменение на коэффициент за проход: остаточные колебания выше трёх полос отклика — `D −10 %`, ниже — `P −10 %`; перерегулирование больше 20 % — `P −10 %`; меньше 5 % без колебаний — `P +10 %`; иначе менять нечего. При изменении P у крена и тангажа I = P (wiki), у рыскания I = 0.1·P (как у AutoTune). Пределы AutoTune: P от 0.01 до 2.0, D не больше 0.2; значение за пределом ограничивается им, а если предел не даёт сдвинуть P в нужную сторону — без изменений (в обоих случаях с пометкой «ограничено»).

Варианты: «Как в логе», «По правилам» (рекомендуется), P ±10 %, D ±10 % (при D > 0) и «Свой» после правки формы. Прогноз каждого варианта — отклик, частота среза и запас фазы — строится из измеренной характеристики «цель → факт» и модели регулятора `AC_PID` (`FLTE`, `FLTD`, FF, как в `AC_PID.cpp`) с учётом фильтров, принятых на шагах 2–3, а не из оценки объекта по замкнутому контуру (она смещена). Прогноз показывается, только если он достоверен: проверки качества пройдены, модель регулятора сходится с данными лога (модуль ±10 %, фаза ±10° на 2–20 Гц), когерентность на частоте среза не ниже 0.5. Отметки — запас фазы ниже 30°, запас хуже лога больше чем на 5°, перерегулирование в прогнозе выше 20 %, контур или прогноз неустойчив — предупреждают, но выбор не блокируют; если отмечен «По правилам», вердикт называет лучший неотмеченный вариант.

Без `PIDR/PIDP/PIDY` шаг работает по `RATE`: отклик и правила есть, прогноза нет — цель там записана до фильтра `FLTT`, а выход — вместе с FF. При частоте лога PID ниже 99 Гц (без ATTITUDE_FAST в `LOG_BITMASK` PID пишутся с 10 Гц) отклик не считается: вердикт шага и проверка шага 0 советуют включить ATTITUDE_FAST. Окно FFT шага влияет только на спектр D и выхода (и шум D) и отклик PIDReview на графике. «Принять» сохраняет все три оси; файла `.param` на шаге нет — итоговый файл собирает сводка (шаг 5).

### Как шаг 5 собирает итог

Сводка перестраивается при каждом показе шага по принятому на шагах 2–4. Шаг 2 даёт `INS_GYRO_FILTER`, `SCHED_LOOP_RATE`, `INS_HNTCH_*` и `INS_HNTC2_*`; шаг 3 — `INS_GYRO_FILTER`, `INS_ACCEL_FILTER`, `ATC_RAT_*_FLTT/FLTE/FLTD` и пределы ускорения под именами лога; шаг 4 — `ATC_RAT_*_P/I/D`. Пересекается только `INS_GYRO_FILTER`, и по нему побеждает шаг 3: он считает от notch шага 2. Если оба шага приняты с разными значениями, под таблицей — строка «INS_GYRO_FILTER: шаг 2 — X, шаг 3 — Y, в файл идёт шаг 3». Непринятый шаг ничего не меняет: его параметры остаются как в логе.

У QuadPlane шаг 3 даёт `Q_A_RAT_*_FLTT/FLTE/FLTD` и пределы ускорения `Q_A_ACCEL_*_MAX` или `Q_A_ACC_*_MAX` (имена лога), файл `<лог>_tune.param` — с ними; строка шага 4 в таблице шагов — «недоступен» с текстом закрытого шага (как подсказка кнопки шага 4). Надписи шага с диапазоном шагов — по шагам аппарата: у Copter «Что принято на шагах 2–4», «Принятое на шагах 2–4», «Менять нечего: ни один из шагов 2–4 не принят», «шаги 2–4 — сбылся ли прогноз»; у QuadPlane — «2–3» (одно правило диапазона — `summary_steps_range` в `core/summary.js`). Описание для пункта о перезагрузке у `Q_A_<X>` берётся у `ATC_<X>`, как на шаге 3. Лог неподдержанного вида (профиля нет) — «менять нечего».

«Было» — последнее значение в логе, как на шагах 2–4. Параметр изменён, если принятое отличается от лога как float32 (0.7 из формы и 0.699999988 из лога — одно); маски сравниваются как целые, `*_HMNCS` — без знака по размеру маски. Параметра нет в логе — он не изменён и не пишется. Исключение — включаемый notch: если `INS_HNTCH_ENABLE` или `INS_HNTC2_ENABLE` в логе 0 (или нет), а принято больше 0, прошивка скрывала остальные поля notch, поэтому изменены все его поля, «было» — «нет в логе». `*_ESCMSK` сравнивается и пишется, только если он есть у аппарата — записан в логе или версия фильтра не ниже 4, как в «Сохранить .param» шага 2. Значение ненадёжной оси шага 4, поправленное вручную, помечается «ось ненадёжна — значение введено вручную».

Таблица «было → станет» и файл `.param` («Скачать .param», имя `<лог>_tune.param`) — только изменённые параметры: что поменяли в Mission Planner после полёта, файл не перезапишет. Неизменённые — в свёрнутом списке «без изменений». Запись — как у шага 2: кратчайшая запись float32, натуральный порядок имён, маски HMNCS при 8 битах — со знаком. Изменений нет — «Скачать .param» и «Запомнить проход» выключены.

«Принять» на шагах 2–4 сохраняет отпечаток входов: интервал анализа, у шагов 2–3 ещё ключ FFT шага 1 и версию фильтра, и действующие отличия от лога на шагах до этого — изменённые строки итога, а не принятое целиком: шаг, принятый «Как в логе», ничего не меняет и следующий шаг устаревшим не делает. У шага 4 из этих отличий берутся только те, от которых зависит его прогноз, — notch, `INS_GYRO_FILTER`, `FLTE` и `FLTD`, как в его собственной проверке: другие пределы ускорения, `FLTT` и `INS_ACCEL_FILTER` шага 3 или `SCHED_LOOP_RATE` шага 2 (модель регулятора считается на частоте контура лога) его устаревшим не делают. Сводка считает отпечаток заново; не совпал — шаг «устарело» с советом принять его заново и кнопкой «К шагу N», а в вердикте самого шага — «Принято раньше… — проверьте и примите заново». Это предупреждение, а не запрет: файл скачать можно. Ограничение: ключ FFT — последнего расчёта шага 1, поэтому смена окна FFT на шаге 0 не делает принятое устаревшим, пока шаг 1 не пересчитан.

Вердикт — «Готово: изменено N параметров» или предупреждение, если есть устаревшее, отметки шагов (хуже лога, запас фазы и т. п.) или оси шага 4 без надёжного измерения; ничего не принято — «менять нечего». У принятого шага — короткий итог к логу: шаг 2 — полоса и задержка на 30 Гц, шаг 3 — шум гироскопа, шум D и задержка путей P и D, шаг 4 — по осям прогноз перерегулирования и запаса фазы или «ненадёжно».

«Что сделать перед следующим полётом» — по порядку: проверки шага 0 с предупреждением или ошибкой и их «что сделать» (кроме тех, о которых есть пункт подготовки); пункты подготовки к следующему полёту и общий пункт о файле `_prep.param` (раздел «Как готовить следующий полёт»); включаемый notch — сначала записать его `ENABLE = 1`, обновить список параметров и загрузить файл ещё раз; перезагрузить полётный контроллер, если изменены параметры с признаком `RebootRequired` в метаданных (`SCHED_LOOP_RATE`, `INS_HNTC*_HMNCS`, `INS_HNTC*_OPTS`, `INS_HNTC*_REF`; метаданные не загрузились — общий совет перезагрузить); тестовый полёт для осей шага 4 без надёжного измерения (из принятого, а если шаг 4 не принят — из посчитанного); последним, если есть изменения, — слетать тем же профилем и загрузить лог в мастер.

Печать («Печать» или Ctrl+P на шаге 5) — только сводка на белом фоне, без навигации, кнопок и графиков, с шапкой «Мастер настройки · лог · аппарат · дата печати»; список «без изменений» на время печати раскрывается, строки таблиц не рвутся между страницами. Печатается показанный шаг: Ctrl+P на других шагах печатает их.

### Как готовить следующий полёт

**Зачем.** Блок «Подготовка к следующему полёту» на шаге 0 проверяет параметры **до** полёта: будет ли в следующем логе всё, что нужно мастеру для выбранной цели, — чтобы не тратить вылет (на втором логе проекта, `1 01.01.1970 2-00-00.bin`, весь полёт прошёл в STABILIZE, ACRO на переключателе не было, и шаг 4 PID не дал). Правила — только качество лога; из безопасности — одно: на переключателе остаётся положение с самовыравниванием для выхода из Acro. Дизайн — `docs/plans/2026-10-30-tune-wizard-stage7-design.md`.

**Порядок работы.**

1. Сохранить параметры аппарата в файл `.param` в Mission Planner (экран Full Parameter List) — или просто загрузить в мастер последний лог.
2. На шаге 0 — «Проверить .param…» (лог не нужен).
3. Выбрать цель полёта.
4. Пройти список: СТОП — без исправления лог для этой цели не годится (у «Выход из ACRO» — лететь небезопасно), ВНИМ — лететь можно, с оговоркой. При цели с PID — проверить в таблице положение ACRO и положение выхода.
5. «Скачать .param исправлений», загрузить файл в Mission Planner (там же, Full Parameter List) и записать в контроллер; если заметка под кнопками просит — перезагрузить полётный контроллер.
6. «Печать плана» и полёт по плану; после полёта — лог в мастер.

**Источник параметров.** Параметры берутся из загруженного лога (блок — под проверками лога) или из файла `.param`, выбранного кнопкой «Проверить .param…» рядом с «Выбрать лог…». Файл можно проверить и без лога: тогда шаг 0 показывает только этот блок, шаги 1–5 недоступны. Файл важнее параметров лога (обычно его сохраняют после полёта, поправив параметры): строка источника это говорит, загрузка лога файл не сбрасывает, «Убрать файл» возвращает к параметрам лога. Даже при выбранном файле газ висения и предупреждения шага 0 берутся из лога. Вид аппарата: у лога — вид лога (раздел «QuadPlane (VTOL-часть ArduPlane)»), у файла — по признаку в нём: есть `ATC_RAT_RLL_P` — Copter, `Q_A_RAT_RLL_P` — QuadPlane (параметры `Q_*` в файле есть, только если `Q_ENABLE` ≠ 0). Отказ в вердикте, без списка, файла и плана: лог не Copter и не QuadPlane; файл без обоих признаков («не похож на их параметры»); файл и лог разных видов — «Файл «…» — <вид>, лог — <вид>: выберите файл этого аппарата или уберите файл», а при логе неподдержанного вида — «… (не поддержан): проверить файл можно без лога (перезагрузите страницу и выберите только файл) или с логом <вид файла>». Без лога годится файл любого поддержанного вида. Пояснение цели под отказом — по виду лога. Газ висения из лога («Обучение газа висения» ниже) берётся, только если лог того же вида, что источник. Файл без строк «ИМЯ,значение» или с именами, не похожими на параметры (например, двоичный лог), — «не файл параметров ArduPilot», источник остаётся прежним.

**Цель полёта.** «Фильтры» (шаги 1–3: висение в любом режиме), «PID» (шаг 4: тестовый полёт Acro «Rate Loop Only») или «Фильтры и PID» (оба в одном полёте, по умолчанию); у QuadPlane пояснения свои: «шаги 1–3: висение в Q-режиме», «лог QACRO для будущего шага 4», «висение и QACRO в одном полёте». Проверяются только правила цели. Выбор запоминается в браузере (`localStorage`, ключ `tunewizard_prep_goal`; хранилище недоступно — цель по умолчанию). Список — как проверки лога (OK / ВНИМ / СТОП, что найдено, что сделать), вердикт — «Готово к полёту: <цель>», «С оговорками: N предупреждений» или «Не готово: N блокирующих проблем».

**Правила.** По порядку списка; в скобках — цели, к которым правило относится. У правил в `core/prep.js` пометки источника: [код] — место в коде ArduPilot, [наше] — решение мастера, [решение пользователя 30.10.2026]. Ниже — правила Copter; чем отличаются правила QuadPlane — после списка.

- «Запись лога» (фильтры, PID) — в `LOG_BACKEND_TYPE` бит 0 (File) или 2 (Block); нет обоих — СТОП, в файл — бит File.
- «Сообщения PID» (PID) — бит 12 (PID) в `LOG_BITMASK`; нет — СТОП, в файл — бит.
- «Частота PID и RATE» (PID) — бит 0 (ATTITUDE_FAST) в `LOG_BITMASK`: без него PID и RATE пишутся с 10 Гц, и отклик шага 4 не считается; нет — СТОП, в файл — бит.
- «Запись гироскопа» (фильтры) — raw (`INS_RAW_LOG_OPT` бит 0 или 1, или бит 19 IMU_RAW в `LOG_BITMASK`) или batch (`INS_LOG_BAT_MASK` ≠ 0); ни того ни другого — СТОП, в файл — batch `INS_LOG_BAT_MASK = 1`, `INS_LOG_BAT_OPT = 4` (работает на любой плате), в «что сделать» ещё подсказка raw для плат H7 и быстрее — `INS_RAW_LOG_OPT = 9`: биты 0 и 3, основной гироскоп до и после фильтров (бит 0 сам включает raw-запись, бит IMU_RAW не нужен); прошивка без `INS_RAW_LOG_OPT` — бит IMU_RAW. Raw и batch вместе — оценивается raw: его берёт мастер.
- «До/после фильтров» (фильтры) — по записи после исправления предыдущего пункта: raw — бит 3 `INS_RAW_LOG_OPT`, только после или только до фильтров — ВНИМ, в файл: бит 3 (+8) добавляется, бит 2 (−4) снимается; batch — только бит 2 `INS_LOG_BAT_OPT` (до и после) — OK; бит 2 с битом 1, только после или только до фильтров — ВНИМ, в файл `INS_LOG_BAT_OPT = 4` (с битом 1 обе половины пишутся после фильтров, а с битами 0 и 1 на Invensense v1/v2 — обе до); бит 2 с битом 0 без бита 1 — по типу гироскопа (ниже); batch из файла — OK. **Бит 0 (Sensor-Rate) с битом 2** (уточнено на этапе 9, `check_sensor_rate_prepost` в `core/checks.js` — одно правило для шага 0 и подготовки, у Copter и QuadPlane): выборку на частоте датчика, при которой обе половины batch сырые, до фильтров, включают только драйверы Invensense v1 и v2 по SPI (`AP_InertialSensor_Invensense.cpp:922`, `AP_InertialSensor_Invensensev2.cpp:638`; типы MPU6000, MPU9250, ICM20602, ICM20601, ICM20789, ICM20689, ICM20648, ICM20649, ICM20948); на остальных датчиках бит 0 batch не действует. Тип — по `INS_GYR_ID`, `INS_GYR2_ID`, … гироскопов из `INS_LOG_BAT_MASK` (`Libraries/DecodeDevID.js`, как подпись датчика шага 1): есть Invensense v1/v2 по SPI — ВНИМ и в файл `INS_LOG_BAT_OPT = 4`; тип не определить (нет `INS_GYR*_ID`) — ВНИМ с оговоркой «если датчик Invensense v1/v2»; иначе — OK с названием датчика (у DroneCAN — «DroneCAN»). `INS_GYR*_ID = 0` — гироскопа нет (ID найденного прошивка записывает при запуске), он пропускается. На третьем логе (ICM45686, `INS_LOG_BAT_OPT = 5`) «после» — настоящие данные после фильтров: OK.
- «Буфер лога» (фильтры; только при raw) — `LOG_FILE_BUFSIZE` ниже 50 КиБ — ВНИМ, в файл 64: на втором логе при 8 КиБ поток GYR рвался каждую секунду.
- «Обороты для notch» (фильтры) — включённый notch по ESC (`INS_HNTCH_MODE` или `INS_HNTC2_MODE` = 3), а `SERVO_BLH_BDMASK` = 0 и ни один `SERIAL0–9_PROTOCOL` не 16 (телеметрия ESC) — ВНИМ, в файл ничего: зависит от регуляторов.
- «ACRO на переключателе» (PID) — ACRO (1) в одном из `FLTMODE1–6`; нет — СТОП, в файл `FLTMODE<N> = 1` выбранного положения.
- «Выход из ACRO» (PID) — по режимам после записи файла: кроме ACRO, есть положение с самовыравниванием (STABILIZE, ALT_HOLD, LOITER, POSHOLD) — OK с напоминанием проверить, что тумблер до него достаёт; нет — СТОП, в файл ничего (выбор пользователя).
- «Acro „Rate Loop Only“» (PID) — бит 1 в `ACRO_OPTIONS`; нет — СТОП, в файл: бит 1 (+2) добавляется, бит 0 (Air-mode) не трогается.
- «Тренер Acro» (PID) — `ACRO_TRAINER = 0`: заводское значение 2 подмешивает в цель выравнивание по углу и в Rate Loop Only; не 0 — СТОП, в файл 0.
- «Быстрый поток контура» (PID) — `FSTRATE_ENABLE` > 0 — ВНИМ без «что сделать»: оговорка к прогнозу шага 4 (модель регулятора считается на `SCHED_LOOP_RATE`).
- «Обучение газа висения» (фильтры) — `MOT_HOVER_LEARN = 2` — OK; иначе при предупреждении шага 0 «Газ висения» — ВНИМ, в файл 2; без лога или без расхождения — OK с советом.

**Правила QuadPlane** (дизайн этапа 9, раздел 9): правила записи лога и фильтров («Запись лога», «Запись гироскопа», «До/после фильтров», «Буфер лога», «Обороты для notch») — общие с Copter (тот же код AP_Logger, AP_InertialSensor и AP_BLHeli; IMU_RAW — тоже бит 19); остальные — по профилю, всего 10:

- «Сообщения PID» нет: PIQR/PIQP/PIQY пишутся вместе с ATT без своего бита, бит 12 у Plane — CAMERA;
- «Частота PID VTOL» (PID) — бит 20 ATTITUDE_FULLRATE в `LOG_BITMASK`: без него PIQx — 25 Гц при бите ATTITUDE_FAST, 10 Гц при одном ATTITUDE_MED, без обоих не пишутся вовсе (фраза та же, что у проверки шага 0, — `check_plane_pid_rate_text`); нет — СТОП, в файл — бит 20 (+1048576: заводская маска 65535 → 1114111). Бит 0 вместе с ним не нужен: `Log_Write_FullRate` проверяет только бит 20 (на логе не проверено);
- «QACRO на переключателе» (PID) — QACRO (23) в одном из `FLTMODE1–6`; нет — СТОП, в файл `FLTMODE<N> = 23`;
- «Выход из QACRO» (PID) — QSTABILIZE (17), QHOVER (18) или QLOITER (19) на другом положении; нет — СТОП;
- «QACRO без удержания угла» (PID) — `ACRO_LOCKING = 0`: в QACRO только контур скорости (как Acro «Rate Loop Only» у Copter), при 1 и 2 удерживается угол (поправка углового контура); не 0 — СТОП, в файл 0;
- «Тренер Acro» и «Быстрый поток контура» нет: тренера Acro и `FSTRATE_*` в Plane нет;
- «Обучение газа висения» (фильтры) — `Q_M_HOVER_LEARN = 2`, логика та же, что у Copter; совет — висение не меньше 30 с в QHOVER или QLOITER, с условиями обучения из раздела «QuadPlane (VTOL-часть ArduPlane)».

**Нет параметра.** Параметра, нужного правилу, нет — ВНИМ «Параметра X нет — проверьте версию прошивки», в файл ничего. Исключения: нет `FSTRATE_ENABLE` — OK (быстрого потока нет в прошивке или на плате); нет `INS_HNTC2_ENABLE` или `SERVO_BLH_BDMASK` — второй notch и двунаправленный DShot считаются выключенными.

**Чего правила не проверяют.** Вибрации, clipping и пришли ли обороты — проверки лога шага 0 (план полёта ссылается на их предупреждения); разрывы потока GYR видны на шаге 1 (окно FFT не даёт окон), хватило ли манёвров — на шаге 4; датчик батареи и то, в какое положение тумблера попадает режим, мастер не проверяет.

**Положение для ACRO.** При цели с PID под списком — таблица положений переключателя: положение, PWM, режим сейчас. PWM положений — как в прошивке (`RC_Channel.cpp`): до 1230, 1231–1360, 1361–1490, 1491–1620, 1621–1749, от 1750. Если ACRO нет ни в одном положении — поле «Положение для ACRO» (`FLTMODE1–6` с режимом сейчас и PWM): предложено положение 6 (верхнее положение трёхпозиционного тумблера), если после замены остаётся положение выхода, иначе ничего не выбрано. Положение с ACRO (уже стоящим или после записи файла) в таблице выделено; у выбранного — пометка «станет ACRO (файл исправлений)», у первого положения выхода — «выход из ACRO» (когда ACRO уже стоит или выбрано). Выбор действует для текущего источника: у нового файла или лога — снова предложение. У QuadPlane — то же для QACRO («Положение для QACRO», «станет QACRO», «выход из QACRO»), режимы в таблице — с именами Plane (номер ACRO Copter, 1, у Plane — CIRCLE), а в подписи таблицы — канал переключателя: «· канал FLTMODE_CH = N» или «· канал FLTMODE_CH (по умолчанию 8)», если параметра нет (у Copter подпись без канала, как раньше). Положения и PWM у Plane те же (`read_6pos_switch`).

**Файл `_prep.param`.** «Скачать .param исправлений» пишет только изменения: значение, равное текущему (как float32), не пишется, правила на одну маску (`LOG_BITMASK`) складываются в одно значение; запись — как у сводки (`param_file_text`). Имя — `<лог или файл без расширения>_prep.param`. Менять нечего — кнопка выключена. Заметка под кнопками перечисляет параметры файла и, если в нём есть `INS_LOG_BAT_MASK`, `INS_LOG_BAT_OPT`, `LOG_BACKEND_TYPE` или `LOG_FILE_BUFSIZE`, просит после записи перезагрузить полётный контроллер. Файл отдельный от `_tune.param` шага 5: подготовка к полёту и настройка не смешиваются, память прохода его не учитывает.

**План полёта.** Пункты по цели: «До полёта: …» для предупреждений шага 0 о вибрациях, clipping и оборотах (если лог загружен); фильтры — взлёт в STABILIZE или ALT_HOLD, висение не меньше 30 с (лучше 60) без движений стиками; PID — безопасная высота, ACRO положением N (с PWM), 2–3 минуты резких отклонений стиков по одной оси — крен, тангаж, рыскание — с разной амплитудой (мастеру нужно не меньше 10 с участков с целью скорости от 20 °/с), выход положением с самовыравниванием; обе цели — сначала висение, потом Acro. Положения выхода нет — вместо пунктов Acro запрет включать ACRO. Последним — посадка и загрузка лога, после Acro — на шаге 4 «Интервал — участок ACRO». У QuadPlane: взлёт в QSTABILIZE или QHOVER, висение без стиков в Q-режиме («VTOL-участки AUTO и GUIDED шаги 1–3 не берут»); QACRO положением N, у tailsitter — «крен VTOL — стиком руля направления, рыскание — элеронами»; выход — положением QSTABILIZE, QHOVER или QLOITER («в QACRO аппарат сам не выравнивается»); требования мастера к участкам Acro не называются (шага 4 пока нет), последний пункт — «загрузите лог в мастер и сохраните лог: шаг 4 для QuadPlane — следующим этапом».

**Печать плана.** «Печать плана» — на белом фоне только блок подготовки: шапка «Мастер настройки · Подготовка к полёту · цель „…“ · файл или лог · дата», пояснение цели, строка источника, вердикт, список, таблица положений, заметка о файле и план, без полей и кнопок. Ctrl+P без кнопки печатает шаг 0 целиком, как раньше.

**Сводка шага 5.** В «что сделать перед следующим полётом» — пункты подготовки с предупреждением или ошибкой и их «что сделать», по тому же источнику, цели и положению ACRO, что блок; пункты без «что сделать» (быстрый поток, нет параметра) не попадают. За ними — общий пункт «Исправления подготовки — в файле `<имя>_prep.param` (шаг 0, „Подготовка к следующему полёту“)», с перезагрузкой, если она нужна: этих значений нет в `_tune.param`. Проверка шага 0 не выводится, если о том же есть такой пункт подготовки — он конкретнее: «Сообщения PID» — при «Сообщения PID» или «Частота PID и RATE», «Данные гироскопа» — при «Запись гироскопа», «До/после фильтров» — при «До/после фильтров», «Газ висения» — при «Обучение газа висения» (у QuadPlane — «Сообщения PID VTOL» при «Частота PID VTOL»). «Источник трекинга notch» (пришли ли обороты в логе) и тестовый полёт по осям шага 4 остаются.

**Проверки шага 0 о записи гироскопа.** Они — по тем же правилам, что «Запись гироскопа» и «До/после фильтров» выше: «Данные гироскопа» без записи советует те же batch и raw, «До/после фильтров» на batch-логе с битом 2 `INS_LOG_BAT_OPT` вместе с битом 1, а с битом 0 — на Invensense v1/v2 по SPI или при неизвестном типе гироскопа (то же правило по типу, `check_sensor_rate_prepost`) — предупреждение с исправлением `INS_LOG_BAT_OPT = 4` и перезагрузкой. Разница: запись только до фильтров шаг 0 считает OK — он оценивает уже записанный лог, оценка «станет» тогда строится расчётом (`core/checks.js`), а подготовка — ВНИМ: следующий полёт можно записать с реальным «после» (`core/prep.js`).

### Память прохода

Мастер помнит последний проход каждого аппарата: изменённые параметры («было» и «станет») и оценки принятых шагов для проверки прогноза. Аппарат узнаётся по строке полётного контроллера из MSG — плата и уникальный номер процессора, например `StellarH7V2 0034002E 35335104 39363630`; она есть и в обезличенных логах. Без неё ключ запасной — номер платы APJ из VER, рама и имя лога: такой проход найдётся только для того же файла. Вид аппарата — в ключе: у Copter ключ прежний (`fc:<строка контроллера>` или запасной `log:…` — старые проходы находятся), у QuadPlane впереди `quadplane·` (`quadplane·fc:…`): одна плата на Copter и на QuadPlane — разные аппараты, и «применено» не сравнивает `ATC_*` с `Q_A_*`. В записи — поле `kind` (нет — Copter), версия формата прежняя; рама запасного ключа QuadPlane — из «QuadPlane Frame: …» MSG.

Память лежит в `localStorage` этого браузера (ключ `tunewizard_v1`, не больше 20 аппаратов — при переполнении удаляется самый старый проход); переноса между браузерами нет. Она привязана к адресу страницы: у `http://127.0.0.1:8000` и `http://localhost:8000` память разная — открывайте мастер всегда по одному адресу (он показан в заметке под кнопками шага 5). Хранилище недоступно (приватный режим, запрет) — сводка пишет, что браузер не даёт сохранить память, остальное работает. Битые записи при загрузке лога отбрасываются с предупреждением (уцелевшие переписываются без них); память другой версии формата или испорченный JSON при загрузке не трогаются — только предупреждение, что их заменит сохранение прохода на шаге 5.

Проход сохраняется при «Скачать .param» (скачанный файл — намерение применить) и кнопкой «Запомнить проход» (значения вводятся вручную); проход того же аппарата заменяется. «Запомнить проход» доступна, когда принят хотя бы один шаг, и без изменений: такой проход закрывает прошлый проход аппарата (шаг 0 его не показывает) — иначе на сошедшемся логе старый проход жил бы вечно; «Скачать .param» без изменений выключена, файла нет. Оценки устаревшего шага и шага, чьё значение перекрыто другим, не сохраняются: прогноз считался не для применяемой конфигурации. Перекрытие — расхождение `INS_GYRO_FILTER` шагов 2 и 3 между значениями, отличными от лога: шаг 2, оставивший значение лога, с шагом 3 не расходится, а шаг 2 со своим значением и шаг 3, вернувший лог, — расходятся (сводка пишет об этом и в вердикте).

Шаг 0 после загрузки лога показывает блок «Прошлый проход»: дату и лог прошлого прохода, таблицу «предлагалось · в логе сейчас» с итогом по параметру — «применено» (равно как float32 или маска), «другое значение», «нет в логе» — и «Применено K из N». Если значения лога равны «было» прошлого прохода и имя лога то же — «это лог прошлого прохода — значения ещё не применялись». Лог без строки контроллера — список сохранённых проходов для выбора (проход того же файла выбран сразу); в этом списке и в списке «Проход этого аппарата не найден» ниже — только проходы того же вида аппарата (Copter или QuadPlane). Прохода этого аппарата в памяти нет вовсе, а проходы других есть (например, после замены полётного контроллера строка контроллера и ключ сменились) — тоже список, ничего не выбрано, с подписью «Проход этого аппарата не найден — выбрать другой». «Забыть» удаляет только показанный проход: если его уже заменило более новое сохранение, оно остаётся. Прохода нет — блока нет. Маска `INS_HNTCH_HMNCS` сравнивается по большему из размеров маски прохода и нового лога (после смены версии фильтра 2 → 3 маска 32-битная).

Шаги 2–4 под вердиктом (на шаге 4 — для оси открытой вкладки) показывают строку «Прошлый проход (дата), было → прогноз → в этом логе: …»: оценка лога прошлого прохода, прогноз для принятого и оценка варианта «Как в логе» нового лога. Шаг 2 — полоса и задержка на 30 Гц, шаг 3 — шум гироскопа, шум D и задержка путей P и D на 30 Гц (шум зависит и от полёта — газа, манёвров), шаг 4 — перерегулирование, нарастание и запас фазы. Строка есть, только если в новом логе стоят все изменённые параметры прошлого прохода по шагам 2–N (на шаге 4 — шагов 2–3 и этой оси): прогноз шага N считался от принятого на шагах до него. Иначе — «применены не все — сравнивать нечего»; шаг (ось) в прошлом проходе ничего не менял — строки нет. Загружен сам лог прошлого прохода (шаг 0 пишет «это лог прошлого прохода») — строк нет: значения ещё не применялись. Для строки шага 4 из параметров шагов 2–3 считаются только те, от которых зависит его прогноз: поля notch, `INS_GYRO_FILTER`, FLTE и FLTD (неприменённый FLTT, `INS_ACCEL_FILTER`, предел ускорения или `SCHED_LOOP_RATE` строку не отменяют). Строки шага 2 нет, если шаг 2 выбрал свой `INS_GYRO_FILTER`, а шаг 3 его перекрыл: прогноз шага 2 считался для другой конфигурации и в память не пишется.

«В этом логе» — только величины конфигурации лога: на шаге 3 — пока шаг 3 считает от notch лога (после «Принять» на шаге 2 с другим notch чисел этого лога нет); на шаге 4 запас фазы — только при достоверном прогнозе оси. Шаг 4 сравнивает ось, только если она надёжна и в прошлом проходе, и сейчас, иначе — «измерение ненадёжно — сравнивать нечем»; при недостоверном прогнозе прошлого прохода запаса фазы нет, в конце — «прогноз был недостоверен».

### Отличия от FilterReview

Расчёты перенесены построчно и сверяются с FilterReview тестом сравнения. Исправлены восемь ошибок исходного кода (список со ссылками на строки — в `docs/plans/2026-10-24-tune-wizard-stage2-design.md`, раздел 2). Заметнее всего первая: FilterReview берёт частоту дискретизации только первого пакета batch-лога; мастер усредняет по всем пакетам, поэтому оси частот могут отличаться на сотые доли процента.

### Отличия от PIDReview

Загрузка, пакеты, FFT и отклик на ступеньку перенесены построчно в `core/pid.js` и сверяются с PIDReview тестом сравнения. Из семи найденных дефектов исходного кода исправлены пять — 1, 2, 3, 5 и 6 (список со ссылками на строки — в шапке `core/pid.js` и в `docs/plans/2026-10-25-tune-wizard-stage4-design.md`, раздел 2); дефект 4 (шумовая добавка винеровской оценки) не исправляется, 7 касается только интерфейса PIDReview. На любом логе действует второй: PIDReview теряет последний отсчёт каждого пакета и чуть завышает частоту (на тестовом логе 400.0023 Гц вместо 400.0002). При логе PID ниже 100 Гц отклик PIDReview искажён, а при заводской маске `LOG_BITMASK` (10 Гц) нулевой; мастер ниже 99 Гц отклик не считает и советует включить ATTITUDE_FAST. Отклик PIDReview в мастере — только график для сравнения; метрики, правила и прогноз считаются по отклику КИХ МНК.

Около 6 с.
- `npm run test:tunewizard-prep` — блок «Подготовка к следующему полёту» в Chrome **без лога**, по синтетическим `tests/fixtures/prep.param` (Copter) и `tests/fixtures/prep_quadplane.param` (QuadPlane): цели, положение для ACRO и QACRO, `_prep.param`, план, печать плана, отказы. Идёт на любом компьютере с Chrome и python.
- `npm run test:tunewizard-serve` — сервер `windows/serve.ps1` и `Мастер настройки.cmd` (только Windows), **без логов**: ответы и запреты HTTP, мастер, FilterReview и PIDReview через этот сервер в Chrome, запуски на занятом порте и коды выхода. С аргументом — на собранной переносной папке: `node tests/tunewizard-serve.cjs "<папка>"` (эту команду печатает сборка) или `npm run test:tunewizard-serve -- "<папка>"`.

Браузерный тест (`test:tunewizard`) и оба теста сравнения (`test:tunewizard-compare`, `test:tunewizard-pid-compare`) запускают браузер через Playwright: нужен либо `CHROME_PATH` — путь к chrome.exe (например, `CHROME_PATH="C:/Users/<пользователь>/AppData/Local/Google/Chrome/Application/chrome.exe" npm run test:tunewizard`), либо установленный Chromium Playwright (`npx playwright install chromium`). Ещё им нужны лог (`TUNEWIZARD_LOG`, иначе тестовый лог `2026-06-18 18-54-42_anon.bin` в `TuneWizard/logs/`, а без него — первый `.bin` там; второму прогону — `TUNEWIZARD_LOG2` или `1 01.01.1970 2-00-00.bin`, третьему — `TUNEWIZARD_LOG3` или `1 01.01.1980 2-00-00.bin`; без лога тест пропускается) и python для локального сервера страниц. `test:tunewizard` привязан к тестовому логу: на другом `.bin` (без тестового лога — например, на втором логе) он падает на проверках памяти прохода и сводки, рассчитанных на тестовый лог. Тесту `test:tunewizard-prep` нужны тот же браузер и python, лог не нужен; `test:tunewizard-serve` — только тот же браузер и Windows, без python и лога.
