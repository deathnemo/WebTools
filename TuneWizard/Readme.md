## Мастер настройки

Пошаговый мастер настройки Copter по одному логу `.bin`: проверка лога, спектр гироскопов, гармонический notch, низкочастотные фильтры, PID по осям, сводка и файл параметров. Помнит прошлый проход аппарата: на следующем логе показывает, что из предложенного применено и сбылся ли прогноз. Объединяет расчёты FilterReview и PIDReview; оригинальные инструменты не изменяет.

Дизайн: `docs/plans/2026-10-23-tune-wizard-design.md`. Планы этапов — в `docs/plans/`.

### Запуск

Из корня репозитория: `python -m http.server --bind 127.0.0.1`, затем `http://127.0.0.1:8000/TuneWizard/` — или главная WebTools `http://127.0.0.1:8000/` и иконка в строке «Мастер настройки» (строка сразу после PID Review; в `index.html` в корне добавлена только она).

Иконка этой строки — `images/TuneWizard_Icon.png`, ширина 400 px (на главной показывается в 200 px, двойная плотность — для чётких экранов). Это снимок шага 2 на тестовом логе: полоса шагов и под ней спектр, в окне 760 px, где полоса шагов встаёт в две строки. Её делает скрипт `tests/tunewizard-icon.cjs`; обновить иконку, если вид шагов заметно изменился: `CHROME_PATH="C:/Users/<пользователь>/AppData/Local/Google/Chrome/Application/chrome.exe" npm run tunewizard:icon` (нужны те же лог и python, что для браузерного теста), посмотреть картинку и закоммитить файл. В обычные проверки скрипт не входит — иначе каждый прогон менял бы картинку.

### Структура

- `index.html`, `wizard.js` — страница, состояние, навигация по шагам, шаг 0 (лог, проверки, график полёта; блок «Прошлый проход» строит `steps/memory.js`).
- `plots.js` — реестр графиков Plotly: цвета из токенов CSS применяются ко всем графикам разом. Тема одна — только тёмная тема «Графит» (решение пользователя 24.10.2026).
- `steps/common.js` — общий модуль шагов: подписи, плитки и ячейки таблиц, вердикт, досчёт шага 1, контекст итога и отпечаток входов принятого шага (`step_summary_context`, «устарело» — `step_accepted_stale`), запуск действий с перехватом ошибок, «Открыть в …», описания параметров из метаданных (и флаг сбоя их загрузки), каркас механизма правок полей шагов 3–4, куски графиков.
- `steps/step1.js` — шаг 1 «Спектр до фильтров»: панель настроек спектра как в FilterReview, средний спектр, спектрограмма, таблица пиков с происхождением.
- `steps/step2.js` — шаг 2 «Гармонический notch»: варианты настроек со сравнением, форма параметров с описаниями ArduPilot, бодэ, метрики, сохранение и загрузка `.param`.
- `steps/step3.js` — шаг 3 «Низкочастотные фильтры»: размер винта, варианты со сравнением, форма параметров с описаниями ArduPilot, спектр гироскопа после фильтров, спектр D-составляющей, бодэ путей P и D, «Принять».
- `steps/step4.js` — шаг 4 «PID по осям»: вкладки осей и сводка, вердикт и плитки метрик оси, проверки качества измерения, варианты с прогнозом, форма `ATC_RAT_*_P/I/D` с описаниями ArduPilot, отклик на ступеньку, цель и факт, спектр D и выхода, бодэ разомкнутого контура, «Принять», «Открыть в PIDReview».
- `steps/step5.js` — шаг 5 «Сводка»: плитки, вердикт, принятое на шагах 2–4 (принят, не принят, устарело — с кнопкой «К шагу N»), параметры «было → станет» и расхождения шагов, свёрнутый список без изменений, «что сделать перед следующим полётом», «Скачать .param», «Запомнить проход», «Печать».
- `steps/memory.js` — память прохода на странице: сохранение прохода, блок «Прошлый проход» шага 0, строки сравнения с прошлым проходом на шагах 2–4.
- `core/` — математика без DOM; те же файлы гоняются под Node:
  - `log.js`, `checks.js` — сведения о логе (в том числе строка полётного контроллера, номер платы и рама) и проверки пригодности;
  - `gyro.js`, `filters.js`, `spectrum.js`, `tracking/*.js` — перенос расчётов FilterReview «минимальным диффом» (загрузка IMU, FFT, фильтры, трекинг notch, спектрограмма);
  - `autofit.js` — автоподбор первого notch (PR ArduPilot/WebTools#363);
  - `metrics.js` — пики спектра и их происхождение (порядковый спектр, запасной метод — медиана частоты моторов);
  - `candidates.js` — варианты notch, оценка шума после фильтров и задержки, выбор лучшего;
  - `lowpass.js` — низкочастотные фильтры: формулы по размеру винта, варианты, оценка (шум гироскопа, шум D-составляющей, задержка путей P и D, бодэ) и отметки;
  - `pid.js` — перенос PIDReview «минимальным диффом» (загрузка `PIDR/PIDP/PIDY` или `RATE`, наборы параметров, пакеты, FFT компонент, отклик на ступеньку); отклик PIDReview — только для графика и сравнения с PIDReview;
  - `pidtune.js` — шаг 4: отклик КИХ МНК, проверки качества измерения, метрики отклика, шум D, режим лога, правила, модель регулятора `AC_PID`, прогноз и его достоверность, варианты и отметки;
  - `params.js` — файл параметров и битовые маски;
  - `summary.js` — итог прохода: строки «было → станет» по принятому на шагах 2–4, порядок источников, текст `.param` из изменённых, отпечаток входов и «устарело», «что сделать перед следующим полётом»;
  - `passmem.js` — память прохода: формат и хранилище, ключ аппарата, запись прохода, «применено», условия строки сравнения.
- `logs/` — локальные логи и скриншоты для проверок, в репозиторий не попадают.

### Как шаг 2 выбирает настройки notch

Мастер считает варианты: как в логе; автоподбор по методу PR #363; автоподбор с гармониками из лога; настройки лога с ослаблением из автоподбора; при необходимости — второй статический notch на оставшемся резонансе рамы (ширина — удвоенная ширина пика по уровню −3 дБ, от 10 Гц до 0.5·F). Каждый вариант оценивается по ожидаемому шуму после фильтров на главных пиках и в полосе 20–400 Гц и по фазовой задержке на 10 и 30 Гц. Рекомендуется самый тихий по полосе среди тех, что не ухудшают ни один пик больше чем на 3 дБ и задержку на 30 Гц больше чем на 0.5 мс относительно лога; иначе — настройки лога. Таблица вариантов видна целиком, любой вариант применяется одной кнопкой.

### Как шаг 3 выбирает низкочастотные фильтры

Размера винта в логе нет: его вводят вручную (4–40″, иначе предупреждение у поля), мастер запоминает его в браузере и подсказывает, какому размеру по формуле соответствует текущий `INS_GYRO_FILTER`. По размеру p в дюймах значения считаются по формулам Mission Planner (Initial Parameter Setup): `INS_GYRO_FILTER = max(20, round(289.22·p^−0.838))`; `FLTT` и `FLTD` крена и тангажа и `FLTT` рыскания — `max(10, INS_GYRO_FILTER / 2)`; `FLTE` крена и тангажа 0, рыскания 2; `INS_ACCEL_FILTER` 10. Пределы ускорения по формуле предлагаются, только если в логе заводские 1100 / 270 °/с²; иначе остаются из лога, потому что их записывает AutoTune. Имена и единицы — по логу: `ATC_ACCEL_*_MAX` в сантиградусах/с² (4.6 и раньше) или `ATC_ACC_*_MAX` в °/с² (новые версии).

Варианты: «Как в логе»; «По размеру винта» (рекомендуется; без размера винта его нет, и рекомендации тоже); «Лог + правило /2» — `INS_GYRO_FILTER` лога, `FLTT` и `FLTD` по правилу /2; «Свой» — значения формы после ручной правки. Notch — принятый на шаге 2, иначе из лога. Метрики показываются относительно «Как в логе»: шум гироскопа после фильтров в полосе 20–400 Гц (как на шаге 2); шум D-составляющей крена и тангажа — модель контура: спектр гироскопа после фильтров сворачивается к `SCHED_LOOP_RATE / 2` и умножается на производную ошибки и фильтры ПИД `FLTE` и `FLTD` первого порядка, как в `AC_PID.cpp`; задержка на 10 и 30 Гц путей P (фильтр гироскопа, notch, `FLTE`) и D (ещё и `FLTD`). `FLTT` стоит на цели и в метрики не входит, рыскание — по правилу, без метрик.

Отметки «шумнее лога» (шум гироскопа или D больше чем на 3 дБ) и «медленнее лога» (путь P или D больше чем на 1 мс на 30 Гц) предупреждают, но выбор не блокируют. При Kd оси 0 — «D выключен»: шум D и путь D этой оси не сравниваются; Kd нет в логе — «неполные данные». Вердикт предупреждает о том, чего модель не учитывает: notch-фильтр ошибки ПИД (`ATC_RAT_RLL/PIT_NEF` ≠ 0) и быстрый поток контура скорости (`FSTRATE_ENABLE` > 0). «Принять» не принимает пустые поля и отрицательные частоты; файла `.param` на шаге нет — итоговый файл собирает сводка (шаг 5).

### Как шаг 4 предлагает PID

По каждой оси мастер измеряет отклик контура скорости на ступеньку методом КИХ МНК: импульсная характеристика «цель → факт» длиной 1 с подбирается методом наименьших квадратов во времени по окнам, где цель не меньше 20 °/с, а отклик — её накопленная сумма. Отклик PIDReview для этого не годится: его плато ниже 1 даже при идеальном слежении, а перерегулирование сжато к 5–20 %, поэтому он остаётся на графике только для сравнения. По отклику КИХ считаются нарастание 10–90 %, перерегулирование, установление в ±5 % от плато, остаточные колебания; по спектру D — шум D-составляющей выше 50 Гц (выше −40 дБ от выхода — предупреждение «горячие моторы» с советом снизить D или `FLTD`).

Измерение проверяется тремя проверками качества: (а) отклик почти не меняется при более сильной регуляризации; (б) первая и вторая половины данных дают тот же отклик; (в) нет подписи углового контура (|T| на 4–12 Гц не выше 1.5). Ещё нужно не меньше 10 с отобранных данных, иначе — «мало манёвров». В обычном полёте Acro при `ATC_RATE_FF_ENAB = 0` угловой контур подмешивается в цель скорости выше 4–5 Гц, и измерение обычно ненадёжно (так у всех осей тестового лога). Тогда отклик показывается с пометкой, правил и прогноза нет, а вердикт советует тестовый полёт: Acro с `ACRO_OPTIONS` «Rate Loop Only» (значение 2, или 3 вместе с Air-mode), 2–3 минуты резких отклонений стиков по каждой оси, в `LOG_BITMASK` включены ATTITUDE_FAST и PID. Такой лог (весь интервал в ACRO с битом «Rate Loop Only») мастер распознаёт и считает точно: проверка (в) там не применяется, а I в модели регулятора с Copter 4.7 умножается на `ATC_ANG_*_P`, как в прошивке.

Правила — только на надёжной оси, одно изменение на коэффициент за проход: остаточные колебания выше трёх полос отклика — `D −10 %`, ниже — `P −10 %`; перерегулирование больше 20 % — `P −10 %`; меньше 5 % без колебаний — `P +10 %`; иначе менять нечего. При изменении P у крена и тангажа I = P (wiki), у рыскания I = 0.1·P (как у AutoTune). Пределы AutoTune: P от 0.01 до 2.0, D не больше 0.2; значение за пределом ограничивается им, а если предел не даёт сдвинуть P в нужную сторону — без изменений (в обоих случаях с пометкой «ограничено»).

Варианты: «Как в логе», «По правилам» (рекомендуется), P ±10 %, D ±10 % (при D > 0) и «Свой» после правки формы. Прогноз каждого варианта — отклик, частота среза и запас фазы — строится из измеренной характеристики «цель → факт» и модели регулятора `AC_PID` (`FLTE`, `FLTD`, FF, как в `AC_PID.cpp`) с учётом фильтров, принятых на шагах 2–3, а не из оценки объекта по замкнутому контуру (она смещена). Прогноз показывается, только если он достоверен: проверки качества пройдены, модель регулятора сходится с данными лога (модуль ±10 %, фаза ±10° на 2–20 Гц), когерентность на частоте среза не ниже 0.5. Отметки — запас фазы ниже 30°, запас хуже лога больше чем на 5°, перерегулирование в прогнозе выше 20 %, контур или прогноз неустойчив — предупреждают, но выбор не блокируют; если отмечен «По правилам», вердикт называет лучший неотмеченный вариант.

Без `PIDR/PIDP/PIDY` шаг работает по `RATE`: отклик и правила есть, прогноза нет — цель там записана до фильтра `FLTT`, а выход — вместе с FF. При частоте лога PID ниже 99 Гц (без ATTITUDE_FAST в `LOG_BITMASK` PID пишутся с 10 Гц) отклик не считается: вердикт шага и проверка шага 0 советуют включить ATTITUDE_FAST. Окно FFT шага влияет только на спектр D и выхода (и шум D) и отклик PIDReview на графике. «Принять» сохраняет все три оси; файла `.param` на шаге нет — итоговый файл собирает сводка (шаг 5).

### Как шаг 5 собирает итог

Сводка перестраивается при каждом показе шага по принятому на шагах 2–4. Шаг 2 даёт `INS_GYRO_FILTER`, `SCHED_LOOP_RATE`, `INS_HNTCH_*` и `INS_HNTC2_*`; шаг 3 — `INS_GYRO_FILTER`, `INS_ACCEL_FILTER`, `ATC_RAT_*_FLTT/FLTE/FLTD` и пределы ускорения под именами лога; шаг 4 — `ATC_RAT_*_P/I/D`. Пересекается только `INS_GYRO_FILTER`, и по нему побеждает шаг 3: он считает от notch шага 2. Если оба шага приняты с разными значениями, под таблицей — строка «INS_GYRO_FILTER: шаг 2 — X, шаг 3 — Y, в файл идёт шаг 3». Непринятый шаг ничего не меняет: его параметры остаются как в логе.

«Было» — последнее значение в логе, как на шагах 2–4. Параметр изменён, если принятое отличается от лога как float32 (0.7 из формы и 0.699999988 из лога — одно); маски сравниваются как целые, `*_HMNCS` — без знака по размеру маски. Параметра нет в логе — он не изменён и не пишется. Исключение — включаемый notch: если `INS_HNTCH_ENABLE` или `INS_HNTC2_ENABLE` в логе 0 (или нет), а принято больше 0, прошивка скрывала остальные поля notch, поэтому изменены все его поля, «было» — «нет в логе». `*_ESCMSK` при версии фильтра ниже 4 не сравнивается и не пишется, как в «Сохранить .param» шага 2. Значение ненадёжной оси шага 4, поправленное вручную, помечается «ось ненадёжна — значение введено вручную».

Таблица «было → станет» и файл `.param` («Скачать .param», имя `<лог>_tune.param`) — только изменённые параметры: что поменяли в Mission Planner после полёта, файл не перезапишет. Неизменённые — в свёрнутом списке «без изменений». Запись — как у шага 2: кратчайшая запись float32, натуральный порядок имён, маски HMNCS при 8 битах — со знаком. Изменений нет — «Скачать .param» и «Запомнить проход» выключены.

«Принять» на шагах 2–4 сохраняет отпечаток входов: интервал анализа, у шагов 2–3 ещё ключ FFT шага 1 и версию фильтра, и действующие отличия от лога на шагах до этого — изменённые строки итога, а не принятое целиком: шаг, принятый «Как в логе», ничего не меняет и следующий шаг устаревшим не делает. У шага 4 из этих отличий берутся только те, от которых зависит его прогноз, — notch, `INS_GYRO_FILTER`, `FLTE` и `FLTD`, как в его собственной проверке: другие пределы ускорения, `FLTT` и `INS_ACCEL_FILTER` шага 3 или `SCHED_LOOP_RATE` шага 2 (модель регулятора считается на частоте контура лога) его устаревшим не делают. Сводка считает отпечаток заново; не совпал — шаг «устарело» с советом принять его заново и кнопкой «К шагу N», а в вердикте самого шага — «Принято раньше… — проверьте и примите заново». Это предупреждение, а не запрет: файл скачать можно. Ограничение: ключ FFT — последнего расчёта шага 1, поэтому смена окна FFT на шаге 0 не делает принятое устаревшим, пока шаг 1 не пересчитан.

Вердикт — «Готово: изменено N параметров» или предупреждение, если есть устаревшее, отметки шагов (хуже лога, запас фазы и т. п.) или оси шага 4 без надёжного измерения; ничего не принято — «менять нечего». У принятого шага — короткий итог к логу: шаг 2 — полоса и задержка на 30 Гц, шаг 3 — шум гироскопа, шум D и задержка путей P и D, шаг 4 — по осям прогноз перерегулирования и запаса фазы или «ненадёжно».

«Что сделать перед следующим полётом» — по порядку: проверки шага 0 с предупреждением или ошибкой и их «что сделать»; включаемый notch — сначала записать его `ENABLE = 1`, обновить список параметров и загрузить файл ещё раз; перезагрузить полётный контроллер, если изменены параметры с признаком `RebootRequired` в метаданных (`SCHED_LOOP_RATE`, `INS_HNTC*_HMNCS`, `INS_HNTC*_OPTS`, `INS_HNTC*_REF`; метаданные не загрузились — общий совет перезагрузить); тестовый полёт для осей шага 4 без надёжного измерения (из принятого, а если шаг 4 не принят — из посчитанного); последним, если есть изменения, — слетать тем же профилем и загрузить лог в мастер.

Печать («Печать» или Ctrl+P на шаге 5) — только сводка на белом фоне, без навигации, кнопок и графиков, с шапкой «Мастер настройки · лог · аппарат · дата печати»; список «без изменений» на время печати раскрывается, строки таблиц не рвутся между страницами. Печатается показанный шаг: Ctrl+P на других шагах печатает их.

### Память прохода

Мастер помнит последний проход каждого аппарата: изменённые параметры («было» и «станет») и оценки принятых шагов для проверки прогноза. Аппарат узнаётся по строке полётного контроллера из MSG — плата и уникальный номер процессора, например `StellarH7V2 0034002E 35335104 39363630`; она есть и в обезличенных логах. Без неё ключ запасной — номер платы APJ из VER, рама и имя лога: такой проход найдётся только для того же файла.

Память лежит в `localStorage` этого браузера (ключ `tunewizard_v1`, не больше 20 аппаратов — при переполнении удаляется самый старый проход); переноса между браузерами нет. Хранилище недоступно (приватный режим, запрет) — сводка пишет, что браузер не даёт сохранить память, остальное работает. Испорченная память или битые записи отбрасываются с предупреждением.

Проход сохраняется при «Скачать .param» (скачанный файл — намерение применить) и кнопкой «Запомнить проход» (значения вводятся вручную); проход того же аппарата заменяется. Оценки устаревшего шага и шага, чьё значение перекрыто другим (расхождение `INS_GYRO_FILTER`), не сохраняются: прогноз считался не для применяемой конфигурации.

Шаг 0 после загрузки лога показывает блок «Прошлый проход»: дату и лог прошлого прохода, таблицу «предлагалось · в логе сейчас» с итогом по параметру — «применено» (равно как float32 или маска), «другое значение», «нет в логе» — и «Применено K из N». Если значения лога равны «было» прошлого прохода и имя лога то же — «это лог прошлого прохода — значения ещё не применялись». Лог без строки контроллера — список сохранённых проходов для выбора (проход того же файла выбран сразу). «Забыть» удаляет только показанный проход: если его уже заменило более новое сохранение, оно остаётся. Прохода нет — блока нет.

Шаги 2–4 под вердиктом (на шаге 4 — для оси открытой вкладки) показывают строку «Прошлый проход (дата), было → прогноз → в этом логе: …»: оценка лога прошлого прохода, прогноз для принятого и оценка варианта «Как в логе» нового лога. Шаг 2 — полоса и задержка на 30 Гц, шаг 3 — шум гироскопа, шум D и задержка путей P и D на 30 Гц (шум зависит и от полёта — газа, манёвров), шаг 4 — перерегулирование, нарастание и запас фазы. Строка есть, только если в новом логе стоят все изменённые параметры прошлого прохода по шагам 2–N (на шаге 4 — шагов 2–3 и этой оси): прогноз шага N считался от принятого на шагах до него. Иначе — «применены не все — сравнивать нечего»; шаг (ось) в прошлом проходе ничего не менял — строки нет. Загружен сам лог прошлого прохода (шаг 0 пишет «это лог прошлого прохода») — строк нет: значения ещё не применялись. Строка шага 2 бывает редко: если шаг 3 принял другой `INS_GYRO_FILTER`, прогноз шага 2 считался для другой конфигурации и в память не пишется.

«В этом логе» — только величины конфигурации лога: на шаге 3 — пока шаг 3 считает от notch лога (после «Принять» на шаге 2 с другим notch чисел этого лога нет); на шаге 4 запас фазы — только при достоверном прогнозе оси. Шаг 4 сравнивает ось, только если она надёжна и в прошлом проходе, и сейчас, иначе — «измерение ненадёжно — сравнивать нечем»; при недостоверном прогнозе прошлого прохода запаса фазы нет, в конце — «прогноз был недостоверен».

### Отличия от FilterReview

Расчёты перенесены построчно и сверяются с FilterReview тестом сравнения. Исправлены восемь ошибок исходного кода (список со ссылками на строки — в `docs/plans/2026-10-24-tune-wizard-stage2-design.md`, раздел 2). Заметнее всего первая: FilterReview берёт частоту дискретизации только первого пакета batch-лога; мастер усредняет по всем пакетам, поэтому оси частот могут отличаться на сотые доли процента.

### Отличия от PIDReview

Загрузка, пакеты, FFT и отклик на ступеньку перенесены построчно в `core/pid.js` и сверяются с PIDReview тестом сравнения. Из семи найденных дефектов исходного кода исправлены пять — 1, 2, 3, 5 и 6 (список со ссылками на строки — в шапке `core/pid.js` и в `docs/plans/2026-10-25-tune-wizard-stage4-design.md`, раздел 2); дефект 4 (шумовая добавка винеровской оценки) не исправляется, 7 касается только интерфейса PIDReview. На любом логе действует второй: PIDReview теряет последний отсчёт каждого пакета и чуть завышает частоту (на тестовом логе 400.0023 Гц вместо 400.0002). При логе PID ниже 100 Гц отклик PIDReview искажён, а при заводской маске `LOG_BITMASK` (10 Гц) нулевой; мастер ниже 99 Гц отклик не считает и советует включить ATTITUDE_FAST. Отклик PIDReview в мастере — только график для сравнения; метрики, правила и прогноз считаются по отклику КИХ МНК.

### Проверки

- `npm run lint` — ESLint по странице и скриптам.
- `npm test` — тесты ядра (вместе с остальными тестами репозитория).
- `npm run test:tunewizard` — строка мастера на главной WebTools (иконка, ссылка) и прогон шагов 0–5 в Chrome на реальном логе, в том числе сводка, файл `.param`, печать, блок «Прошлый проход» и строки сравнения (см. `tests/README.md`).
- `npm run test:tunewizard-compare` — тот же лог в FilterReview и в мастере, поэлементное сравнение спектров, спектрограммы, бодэ и оценки «после».
- `npm run test:tunewizard-pid-compare` — тот же лог в PIDReview и в мастере, поэлементное сравнение отклика на ступеньку (окна, среднее, ось времени) и отчёт, чем от мастера отличается исходный PIDReview.

Браузерный тест (`test:tunewizard`) и оба теста сравнения (`test:tunewizard-compare`, `test:tunewizard-pid-compare`) запускают браузер через Playwright: нужен либо `CHROME_PATH` — путь к chrome.exe (например, `CHROME_PATH="C:/Users/<пользователь>/AppData/Local/Google/Chrome/Application/chrome.exe" npm run test:tunewizard`), либо установленный Chromium Playwright (`npx playwright install chromium`). Ещё им нужны лог (`TUNEWIZARD_LOG` или первый `.bin` в `TuneWizard/logs/`; без лога тест пропускается) и python для локального сервера страниц.
