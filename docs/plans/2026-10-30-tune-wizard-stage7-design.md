# Мастер настройки — этап 7: подготовка к полёту (дизайн)

Дата: 30.10.2026. Статус: утверждён пользователем 30.10.2026 (вместе с предложениями раздела 10). Основа — `2026-10-23-tune-wizard-design.md`; правила шага 0 — `TuneWizard/core/checks.js`, совет тестового полёта — шаг 4 (`step4_test_flight`), «что сделать перед следующим полётом» — `summary_refly` (`core/summary.js`).

Повод: на втором логе (30.10.2026, весь полёт в STABILIZE) шаг 4 не дал PID, а о том, что для тестового полёта нет ACRO на переключателе режимов, пользователь узнал только после разбора лога и `.param`. Мастер должен говорить это **до** полёта.

## 1. Решения пользователя (30.10.2026)

- **Где:** один набор правил в двух местах — на шаге 0 по параметрам загруженного лога (готовность к *следующему* полёту) и отдельным входом «Проверить .param» — без лога или когда параметры поменяли после полёта.
- **Цель полёта выбирается:** «Фильтры» (шаги 1–3: висение в любом режиме), «PID» (шаг 4: тестовый полёт Acro «Rate Loop Only»), «Фильтры и PID» (оба в одном полёте). Проверяется только нужное для выбранной цели.
- **Выход:** список проверок (статус, что не так, что сделать), файл `.param` с исправлениями, план полёта под цель (с печатью).
- **Правила — только качество лога.** Безопасность — только то, без чего тестовый полёт опасен: на переключателе остаётся режим с самовыравниванием для выхода из Acro.

## 2. Что видит пользователь

На шаге 0 под проверками лога — блок «Подготовка к следующему полёту»:

1. Переключатель цели: Фильтры · PID · Фильтры и PID.
2. Строка источника: «по параметрам лога «…»» или «по файлу «1.param»».
3. Список проверок — как проверки лога: значок статуса, заголовок, что найдено (имена и значения параметров), что сделать.
4. Если ACRO на переключателе нет — выбор положения: таблица `FLTMODE1–6` (режим сейчас, диапазон PWM) и поле «Положение для ACRO».
5. «Скачать .param исправлений» (только изменения) и «Печать плана».
6. План полёта по пунктам.

Без лога (загружен только `.param`) шаг 0 показывает только этот блок; шаги 1–5 недоступны, как сейчас без лога.

## 3. Правила

Статусы как у шага 0: ok, warn (полёт даст лог, но хуже), fail (нужное для цели в логе не появится). «В файл» — что пишет `.param` исправлений. Цели: Ф — фильтры, P — PID.

## 4. Источник параметров

- Только лог — параметры лога (`log_params`).
- Только файл — `parse_param_file`; страница оборачивает объект в тот же интерфейс `get(name)`, что у `log_params`.
- Лог и файл — **файл важнее** (обычно его сохранили после полёта); строка источника это говорит, «Убрать файл» возвращает к параметрам лога. Сведения из лога (газ висения, предупреждения шага 0) используются и при файле.

## 5. Выход

- **Список проверок** — правила цели по порядку таблицы раздела 3.
- **Файл `.param` исправлений** — только параметры, которые меняют правила; несколько правил на одну маску (`LOG_BITMASK`) складываются в одно значение. Запись — `param_file_text`, как у сводки. Имя — `<лог или файл>_prep.param`. Параметры с `RebootRequired` (метаданные — `summary_reboot_names`) — строка «после записи перезагрузите полётный контроллер: …». Файл отдельный от `_tune.param` шага 5: подготовка к полёту и настройка не смешиваются, и память прохода её изменения не учитывает.
- **План полёта** — пункты по цели:
  - Ф: взлёт в STABILIZE или ALT_HOLD; висение не меньше 30 с (лучше 60) без движений стиками [wiki, Initial tuning flight — `hover_min_s` checks.js];
  - P: безопасная высота, переход в ACRO положением N; 2–3 минуты резких отклонений стиков с возвратом по одной оси — крен, тангаж, рыскание — с разной амплитудой (мастеру нужно не меньше 10 с участков с целью от 20 °/с — Readme, шаг 4); выход — положением с самовыравниванием; в Acro дрон сам не выравнивается;
  - Ф + P: сначала висение, потом Acro;
  - в конце: посадка, загрузить лог в мастер; на шаге 4 — «Интервал — участок ACRO».
  - Лог загружен и шаг 0 предупреждает (вибрации, clipping, обороты) — пункт «до полёта» с их «что сделать».
- **Печать** — план и список проверок на белом фоне, как печать сводки.

Выбор цели запоминается в браузере (`localStorage`, с перехватом ошибок), по умолчанию «Фильтры и PID».

## 6. Сводка шага 5

В «что сделать перед следующим полётом» (`summary_refly`) — новый источник `prep`: проверки подготовки со статусом warn и fail для выбранной цели — по тому же источнику, что блок шага 0 (файл важнее параметров лога, `prep0_items()`; уточнено при реализации), «заголовок — что сделать». Пункт `test_flight` остаётся: он про оси без надёжного измерения, а `prep` — про конкретные параметры.

Повторы (уточнено при реализации, задача 3): проверка шага 0 не выводится, если о том же есть пункт подготовки warn/fail — он конкретнее и его значение уже в `_prep.param`: `pid_log` ↔ `log_pid`, `log_fast`; `gyro_log` ↔ `gyro_data`; `pre_post` ↔ `gyro_prepost`; `hover_throttle` ↔ `hover_learn` [наше]. `tracking` остаётся: он о том, пришли ли обороты в логе, а не о параметрах.

Общий пункт после пунктов подготовки (ревью задачи 3): если у пунктов подготовки есть изменения для файла — «Исправления подготовки — в файле `<имя>_prep.param` (шаг 0, «Подготовка к следующему полёту»)», и если среди них есть параметры с перезагрузкой (`prep_reboot_names`) — «после записи перезагрузите полётный контроллер: …». Без него сводка не говорила бы, что эти значения не в `_tune.param`, и после чистки повторов потеряла бы перезагрузку.

Batch «до и после» (`INS_LOG_BAT_OPT` бит 2) вместе с битом 1 или битом 0 — warn, исправление — `INS_LOG_BAT_OPT = 4` и перезагрузка, в шаге 0 (`checks.js`) и в подготовке (`gyro_prepost`): с битом 1 без бита 0 обе половины после фильтров (`AP_InertialSensor.h:351–353`); с битом 0 на датчиках с выборкой на частоте датчика batch берёт только сырые отсчёты — обе половины до фильтров (`BatchSampler.cpp:103–115`, `AP_InertialSensor_Backend.cpp:503–508, 727–738`) (ревью задачи 3).

## 7. Код

- `TuneWizard/core/prep.js` — ядро без DOM (под Node в тестах), префикс глобальных имён `prep_` (свободен — проверено `grep` по `Libraries/` и `TuneWizard/`):
  - `prep_rules` — пороги и номера битов с источниками;
  - `prep_check(params, goal, ctx)` → `[{ id, status, title, text, fix, changes }]`; `params.get(name)` → число или null; `goal` — `"filters" | "pid" | "both"`; `ctx = { acro_slot, hover_check }` (`hover_check` — проверка шага 0 «Газ висения» или null);
  - `prep_changes(items)` → объект имя → значение (маски сложены);
  - `prep_mode_slots(params)` → `FLTMODE1–6`: режим, диапазон PWM;
  - `prep_flight_plan(goal, ctx)` → пункты текста.
- `TuneWizard/steps/prep.js` — блок на шаге 0: выбор цели, файл, список, таблица положений, скачивание, печать; подключается после `steps/common.js`.
- `TuneWizard/index.html` — второй выбор файла на шаге 0 (`accept=".param,.parm,.txt"`) и разметка блока; стили — имеющиеся классы `.checks`, `.lab`, `.tablewrap`, тема «Графит».
- `core/summary.js` — источник `prep` в `summary_refly`.

## 8. Попутные исправления

- `checks.js`, совет при отсутствии данных гироскопа: raw — `INS_RAW_LOG_OPT = 9` (основной гироскоп до и после фильтров) вместо «бит IMU_RAW + `INS_RAW_LOG_OPT = 8`»: бит 0 сам включает raw-запись основного гироскопа, а IMU_RAW пишет все гироскопы [код] Backend.cpp:480–487.
- Журнал, раздел 8, второй лог: `GYR[0]` и `GYR[1]` — один гироскоп до и после фильтров (`INS_RAW_LOG_OPT = 9`, при бите 3 после фильтров пишется экземпляром `instance + число гироскопов`), а не «raw двух гироскопов» (сделано вместе с утверждением дизайна).

## 10. Предложенное по умолчанию — утверждено 30.10.2026

- **а) Цель по умолчанию** — «Фильтры и PID», выбор запоминается в браузере.
- **б) Положение для ACRO** — пользователь выбирает из `FLTMODE1–6`; предлагается `FLTMODE6` (верхнее положение трёхпозиционного тумблера, PWM от 1750), если после замены остаётся положение с самовыравниванием; иначе — ничего не предлагается, только выбор.
- **в) Нет записи гироскопа** — в файл batch (`INS_LOG_BAT_MASK = 1`, `INS_LOG_BAT_OPT = 4`): работает на любой плате; raw (`INS_RAW_LOG_OPT = 9`) — подсказкой для плат H7 и быстрее, без записи в файл.
- **г) Буфер лога** — при raw-записи предупреждать ниже 50 КиБ, в файл 64. Порог — наше: 8 КиБ точно мало, 64 у пользователя проверит следующий лог; по итогам порог можно поправить.
- **д) Лог и файл** — файл важнее, «Убрать файл» возвращает к логу.
- **е) Два файла** — `_prep.param` (шаг 0) и `_tune.param` (шаг 5) отдельно.
- **ж) Ветка** — `tune-wizard-next3`, PR внутри форка в конце этапа.
